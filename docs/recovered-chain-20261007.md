# Recovered Chain Continuation — 2026-10-07

This driver continues the recovered ThinkFL/RCA data chain after the Codex recovery workspace has produced four datasets:

- `tt4`
- `ob4`
- `o2`
- `polestar`

It does not start from the older biased adapter. The generated training configs form a fresh chain:

`base Muse -> tt4 -> ob4 -> o2 -> polestar`

The continuation driver is intentionally separate from data recovery. Missing recovered files are a heartbeat wait state, not a permanent failure. Execution is stage-wise: after the shared-runtime eval guard is idle, `tt4` can train as soon as its own recovered dataset is complete, while later stages wait for both their dataset and predecessor adapter.

## Commands

```bash
uv run python scripts/mcp_continue_recovered.py \
  --config configs/sft/recovered-chain-20261007.yaml \
```

## Guarantees

- Validates dataset SHA-256, manifest readiness, recovery complete marker SHA plus writer/judge provider and model, non-empty examples/cases, positive supervised turns, and train-only case membership.
- Rejects split overlap across train/validation/sealed/public partitions.
- Generates distinct stage configs under the continuation workspace, with only stage 2+ using the previous recovered-chain adapter.
- Snapshots the SSH key into a private runtime directory (`0700` dir, `0600` key) so the service does not depend on `/tmp` after startup.
- Syncs only bounded training/runtime files, generated configs, datasets, and manifests. It does not run the scratchpad broad `kt_sync_mcp.sh`.
- On service restart, reconciles KT `training-<tag>.exitcode` plus the final adapter before launching. Completed stages are skipped; launched stages are attached and waited; incomplete existing output dirs are not overwritten. Later missing datasets do not block already-ready earlier stages, but the eval guard still blocks sync/training while the shared eval runtime is active.
- Waits for the existing eval driver to become idle before loading LoRA adapters or starting validation.
- Runs fresh validation on validation partition only; it never uses sealed eval.
- Compares only the fresh base and recovered-chain validation runs generated by this continuation, avoiding retrospective rejudging of existing eval roots.
- Mechanism judge provenance is configured as provider `codex`, model `gpt-6.1-sol`, rubric `v2`. The driver passes `--provider`, `--model`, and `--rubric` through to the Codex mechanism judge/report scripts.

## Limits

- It assumes KT `/home/work/run-mcp-train.sh`, `/home/work/kt_lora_strip_vision.py`, and the vLLM OpenAI endpoint are already present. It does not call the destructive `restart-mcp-train.sh`.
- It does not install Python dependencies on KT.
- If mechanism judging stops with a session-limit/not-started summary, the driver leaves state as `mechanism_judge_resumable` and exits with code `3` for service retry.
