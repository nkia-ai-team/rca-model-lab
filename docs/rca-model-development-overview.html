04 · ThinkFL과의 차이

폐기한 v6와 현재 RL은 다르다

ThinkFL은 단계적으로 최신 정책의 새 조사를 반복 생성한다. v6는 저장된 좋은/나쁜 쌍만 사용한 오프라인 실험이었다.

Current v6

Offline preference refinement

  1. 과거 Student rollout 사용
  2. 교사/성공 궤적을 chosen으로 선택
  3. 높은 점수의 오답을 rejected로 선택
  4. P(chosen) > P(rejected) 학습
  5. 학습 중 환경·새 rollout 없음
→
ThinkFL direction

On-policy progressive GRPO

  1. 현재 Student가 실제 하네스 조사
  2. 같은 사건을 N회 rollout
  3. grader가 각 전체 궤적 채점
  4. 그룹 상대 advantage로 LoRA 갱신
  5. 갱신된 Student가 다시 새 rollout
1.00정확한 root + proof
0.65root 맞음, 증거 부족
0.25증상만 식별
0.00틀림 + 과확신
왜 0/1만 쓰지 않나: 그룹이 [0,0,0,0]이면 advantage가 전부 0이라 배울 수 없다. 다만 특정 도구 실행 자체나 긴 조사에는 보상하지 않는다. 원인·proof·evidence 계약과 연결된 진전만 사용한다.

참고: ThinkFL paper · official repository

06 · 모델이 사용하는 실행 환경

학습 결과를 만드는
네 가지 장치

도구 전체 목록보다 실험 해석에 필요한 계약만 남겼다.

Capability registry

이번 사건에서 실제 존재하는 target·metric·action·source·kind. 모델 생각은 자유롭게 두고 실행만 현실 계약으로 검증한다.

Evidence store/map

원본 metric·log·trace·event 전체와 ID 인덱스. 조회 응답만 cap하며 원본을 300개로 자르지 않는다.

Typed ledger

모든 성공·실패 도구 호출과 evidence refs를 episode JSONL에 append. 현재 중앙 DB와 중간 resume는 없다.

Typed scorer

답과 ledger를 함께 읽어 root, proof, mechanism, refs, status를 채점. SFT 채택·RL reward·평가가 같은 계약을 쓴다.

Ledger 실제 형태
{
  "turn": 4,
  "action": "env_query",
  "target": "food-delivery-payment",
  "ok": true,
  "evidence_refs": ["ev010", "ev011", "ev210", "ev221"]
}

08 · 실제 실행 기록

F15-H 한 번의 조사가
점수가 되기까지

파일 경로가 아니라 저장된 SFT 실행 1회의 입력, 도구 호출, 관측, 최종 답, scorer 판정을 순서대로 보여준다.

1. 사건과 정답

관측된 장애: 같은 시각에 commerce checkout과 food 주문이 함께 실패했다.

실제 근본원인 ①: commerce inventory 테이블의 EXCLUSIVE lock 때문에 예약 쓰기가 대기했고 checkout이 timeout 됐다.

실제 근본원인 ②: 외부 PG의 /pay가 HTTP 429 RATE_LIMITED를 반환했고 payment가 이 값을 상위 요청으로 전달했다.

판단 핵심: 두 장애는 동시에 시작했지만 공통 원인이 아니다. 서로 다른 두 원인을 모두 찾아 분리해야 한다.
