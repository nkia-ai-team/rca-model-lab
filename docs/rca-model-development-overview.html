장애 원인을 직접 조사하고
증거와 함께 답하는 모델

운영 장애가 주어지면 모델이 로그, 메트릭, 트레이스, 이벤트를 직접 조회한다. 조회 결과에서 증상과 근본원인을 구분하고, 어떤 증거로 결론을 내렸는지 함께 답하게 만드는 프로젝트다.

교사 조사 24개로 1차 SFT 완료 20개 장애 유형 사용 강화학습 실험 4개는 기준 모델보다 좋아지지 않음 현재 교사 데이터·채점 규칙 재검사 중 최종 목표: Claude·Codex 이상

이 프로젝트를 처음 보는 사람이 먼저 알아야 할 내용

무엇을 만드는가
장애 알림을 받으면 로그·메트릭·트레이스·이벤트를 직접 조회하고, 근본원인과 근거를 구조화된 형식으로 제출하는 RCA 전용 모델을 만든다.
모델에게 주는 것
장애 발생 시간, 조사 가능한 시스템 목록, 사용할 수 있는 조회 기능이다. 정답 원인과 정답 증거는 주지 않는다.
모델이 해야 하는 것
조회 기능을 여러 번 실행해 원인을 찾고, 원인마다 발생 과정, 지지 증거 ID, 반대 증거 ID, 확신 수준을 제출해야 한다.
지금까지의 결과
교사 조사 24개로 SFT한 모델은 학습 전 모델보다 원인 후보와 증거를 더 잘 찾았다. 그러나 완전한 정답 조건을 만족하는 비율은 아직 낮다.
실패한 시도
완료한 강화학습 v1, v2, v3, v6는 SFT 모델보다 사건 단위 정확도가 좋아지지 않았다. 따라서 실제 사용 모델로 채택하지 않았다.
현재 작업
교사 데이터와 채점 규칙의 정합성을 다시 검사하고 있다. 검사를 통과한 전체 조사 기록으로 SFT를 다시 학습한 뒤, 그 모델이 직접 생성한 여러 조사 결과로 온라인 GRPO를 수행한다.
최종 목표
같은 장애, 같은 조회 기능, 같은 채점 규칙에서 Student 모델이 Claude와 Codex와 비슷하거나 더 높은 RCA 정확도를 내는 것이다.
읽는 순서: 프로젝트 이해만 필요하면 이 요약 다음에 실제 실행 전체 예시로 바로 이동하면 된다. 중간 부분은 어떤 데이터와 학습 방법을 시도했고 왜 폐기했는지 설명하는 연구 기록이다.

무엇을 학습했나

검증된 교사 조사 24개를 턴별로 쪼개지 않고 전체 조사 순서 그대로 SFT했다.

무엇이 개선됐나

바닐라보다 반복 조회가 줄고 실제 원인 후보를 찾는 비율과 증거 인용이 좋아졌다.

무엇이 실패했나

RL v1~v3과 v6는 SFT보다 안정적으로 좋아지지 않아 모두 승격하지 않았다.

지금 무엇을 하나

교사 답의 원인 ID와 증거가 새 채점 규칙에 정확히 맞는지 검사하고, 잘못된 궤적을 교정하고 있다.

02 · 필수 용어

이 문서에서 쓰는 말

아래 용어만 알면 나머지 실험 결과를 읽을 수 있다.

Case정답 근본원인과 관측 데이터가 준비된 장애 사건 1건.
Run / Rollout모델이 한 case를 처음부터 끝까지 한 번 조사한 실행 기록.
Episode질문, 모든 도구 호출, 모든 관측, 최종 답을 합친 전체 조사 기록.
SFT검증된 교사 episode와 같은 행동을 하도록 LoRA로 학습하는 단계.
RL같은 case의 여러 rollout 점수를 비교해 더 나은 조사 행동의 확률을 높이는 단계.
Root F1모델이 찾은 근본원인 집합과 정답 집합의 일치도. 1.0이면 모두 맞음.
Strict correct근본원인뿐 아니라 증명 방식, 증거 ID, 확신 수준까지 모두 통과한 실행.
Majority strict같은 case를 3회 실행했을 때 2회 이상 strict인 사건.
Provisional유력한 원인은 찾았지만 결정적 증명 요건은 아직 충족하지 못한 답.
이 문서의 기준 모델
SFT 모델이다. 검증된 교사 조사 24개를 전체 조사 순서 그대로 학습한 모델이며, 이후 모든 강화학습 결과는 이 모델보다 나아졌는지 비교한다.
현재 결론
SFT로 조사 행동은 개선됐다. 그러나 엄격한 정답률은 아직 낮고, 완료된 강화학습 모델 중 SFT를 확실히 이긴 모델은 없다.

05 · 강화학습 실험과 결과

완료한 강화학습은
아직 SFT를 이기지 못했다

각 실험에서 무엇을 바꿨고, 어떤 문제가 발생했고, 다음 실험을 어떻게 정했는지 기록한다.

SFT · whole episode

기준 정책

검증된 24개 전체 조사 궤적을 LoRA로 모방. 반복 조회가 줄고 root 후보 식별이 개선됐다.

결과
역사적 reward 0.189 / root F1 0.217
결정
모든 RL은 이 SFT 정책 위에서 시작

RL v1 · 종합 reward DAPO

퇴행

20 cases × 4 rollouts. 전체 episode에 상대 advantage를 적용했다. 하지만 턴 수·도구 성공 같은 약한 신호가 틀린 RCA 사이에도 순위를 만들었다.

결과
reward 0.184 / root F1 0.204
문제
빠른 오답이 늦은 오답보다 강화될 수 있음. 실패 episode의 유용한 action까지 억제.
다음
진단 정확도 중심 reward로 축소

RL v2 · diagnosis-only DAPO

퇴행

root F1·exact root·proof·status만 최적화. LR을 낮추고 KL을 높였다.

데이터
80 rollouts, strict success 7/80
신호
20개 중 11개 그룹 reward 동일, 4개 그룹 all-zero
결과
reward 0.177 / root F1 0.190
다음
모든 rollout이 틀린 사건에 teacher anchor 추가

RL v3 · teacher-anchor DAPO

최대 퇴행

검증된 교사 궤적을 양성, Student hard negative를 음성으로 사용. 작은 데이터에서 negative gradient가 조사 정책 전체를 손상시켰다.

결과
reward 0.154 / root F1 0.138
가능 원인
교사/Student 분포 차이. 실패 안의 정상 탐색 token까지 음수 처리.
다음
실패를 밀지 않고 성공만 replay

RFT v4 · positive replay

가능성만 확인

교사 궤적과 exact-root Student 성공만 재학습. 실패 episode에는 음수 gradient를 주지 않았다.

데이터
33 positive episodes, LR 1e-7, KL 0.50
Monitor
SFT 0.229/0.222 → v4 0.281/0.333 (reward/root F1)
제한
당시 model SHA·restore SHA·actor provenance 불완전. 승격 증거 아님.

v5 · progressive per-turn DAPO

미승격

terminal reward와 route step reward를 결합. 새 증거, 결정적 조회, 반복·실패 action에 turn credit을 부여했다.

데이터
80 rollouts
신호
terminal reward가 달랐던 그룹 9/20, 성공·실패가 함께 있던 그룹 4/20
위험
gold target 조회 자체를 보상하면 인과 추론 대신 접근 패턴을 외울 수 있음.

v6 · offline whole-trajectory RPO

승격 실패

좋은 전체 궤적의 확률을 hard negative보다 높이고, 작은 imitation anchor로 SFT 정책 붕괴를 억제한다.

데이터
20 pairs · teacher chosen 16 · Student chosen 4
학습
20 steps · LR 5e-7 · beta 0.10
결과
reward 0.2285→0.2303, root F1 0.2222 유지, strict 2/18 유지
실패
majority strict cases 1/6→0/6. 평균 상승으로 사건 단위 안정성 퇴행을 덮지 않음.
v6에서 발견한 별도 기술 결함: target_modules: all-linear가 vision tower까지 포함했다. vision LoRA B tensor 304개는 0이었지만 multimodal vLLM direct-LoRA profiling이 shape assertion으로 실패했다. 다음부터 model.language_model.* projection만 학습한다.
06 · 현재 강화학습 방향

폐기한 v6와
다음 GRPO는 학습 방식이 다르다

v6는 저장된 좋은 답과 나쁜 답만 사용했다. 다음 GRPO는 현재 모델이 실제 환경에서 새 조사를 생성하고 그 결과로 학습한다.

Current v6

Offline preference refinement

  1. 과거 Student rollout 사용
  2. 교사/성공 궤적을 chosen으로 선택
  3. 높은 점수의 오답을 rejected로 선택
  4. P(chosen) > P(rejected) 학습
  5. 학습 중 환경·새 rollout 없음
→
ThinkFL direction

On-policy progressive GRPO

  1. 현재 Student가 실제 하네스 조사
  2. 같은 사건을 N회 rollout
  3. grader가 각 전체 궤적 채점
  4. 그룹 상대 advantage로 LoRA 갱신
  5. 갱신된 Student가 다시 새 rollout
1.00정확한 root + proof
0.65root 맞음, 증거 부족
0.25증상만 식별
0.00틀림 + 과확신
왜 0/1만 쓰지 않나: 그룹이 [0,0,0,0]이면 advantage가 전부 0이라 배울 수 없다. 다만 특정 도구 실행 자체나 긴 조사에는 보상하지 않는다. 원인·proof·evidence 계약과 연결된 진전만 사용한다.

08 · 모델의 조사 환경

모델이 조사할 때
작동하는 네 구성요소

각 구성요소가 무엇을 제공하고, 무엇을 저장하고, 무엇을 검사하는지 설명한다.

실행 가능 목록
Capability registry

이번 장애에서 조회할 수 있는 서비스, 호스트, 메트릭 이름, 조회 기능을 담은 목록이다. 목록에 없는 이름으로 조회하면 실행 전에 거절한다.

예: target=food-delivery-payment, action=env_slice, source=log.

전체 증거 저장소와 인덱스
Evidence store / map

원본 로그·메트릭·트레이스·이벤트는 모두 보관한다. 각 항목에는 ev221 같은 ID가 붙는다. 한 번의 조회 화면만 크기를 제한하며 원본 268개 자체를 삭제하지 않는다.

조사 실행 기록
Typed ledger

모델이 어떤 조회를 했고, 성공했는지, 어떤 증거 ID를 받았는지를 매 턴 구조화해 추가한다. 실패와 중복 조회도 삭제하지 않는다.

자동 채점기
Typed scorer

최종 답과 조사 기록을 함께 읽는다. 정답 원인 일치, 증명 방식, 증거 ID 유효성, 원인 전파 설명, 확신 상태를 같은 규칙으로 채점한다.

Ledger 실제 형태
{
  "turn": 4,
  "action": "env_query",
  "target": "food-delivery-payment",
  "ok": true,
  "evidence_refs": ["ev010", "ev011", "ev210", "ev221"]
}

10 · 실제 실행 전체 예시

F15-H에서 모델은
무엇을 했고 무엇을 놓쳤나

파일 위치를 나열하지 않는다. 실제 입력, 도구 요청, 도구 응답, 모델의 최종 답, 당시 채점 결과를 순서대로 보여준다.

결론부터: 이 사건에는 두 개의 독립된 근본원인이 있었다. SFT 모델은 외부 PG의 429 오류와 그 증거를 찾았지만 inventory DB의 EXCLUSIVE lock은 찾지 못했다. 그래서 완전 정답이 아니라 부분 정답으로 판정됐다.

1. 사건과 정답

관측된 장애: 같은 시각에 commerce checkout과 food 주문이 함께 실패했다.

실제 근본원인 ①: commerce inventory 테이블의 EXCLUSIVE lock 때문에 예약 쓰기가 대기했고 checkout이 timeout 됐다.

실제 근본원인 ②: 외부 PG의 /pay가 HTTP 429 RATE_LIMITED를 반환했고 payment가 이 값을 상위 요청으로 전달했다.

판단 핵심: 두 장애는 동시에 시작했지만 공통 원인이 아니다. 서로 다른 두 원인을 모두 찾아 분리해야 한다.

3. 실제 입력부터 채점까지

모델 입력

모델은 아래 장애 정보와 조사 가능 목록을 받았다. 근본원인 정답은 포함되지 않았다.

[인시던트] sms.network_interface.rx_packets critical main: tb-w3 장애 창: 10:14:15 ~ 10:46:47 조회 가능: 20개 대상, event/log/metric/trace 사용 가능 action: env_top, env_entity, env_query, env_slice, env_grep, ...
도구 요청

세 번째 조회에서 payment 대상에 429와 PG 실패가 모여 있는 것을 본 뒤, 네 번째 턴에 관련 증거 원문을 요청했다.

{ "action": "env_slice", "arg1": "ev221,ev212,ev210,ev220" }
도구 응답

하네스가 실제 저장소에서 네 증거를 꺼내 모델에게 반환했다.

ev221: PG /pay failed ... 429 Too Many Requests ... RATE_LIMITED ev212: 같은 PG 실패에 대한 warning event ev210: 같은 PG 실패에 대한 caution event ev220: WARN+ 로그 50건의 표본
모델 판단

찾은 원인: 외부 PG가 429 RATE_LIMITED를 반환했고 payment 요청으로 전파됐다.

놓친 원인: inventory의 EXCLUSIVE lock 때문에 checkout 쓰기가 대기한 별도 장애.

제출 상태: provisional. 결정적 증명을 완료하지 못했다고 표시했다.

당시 채점

0.572 reward · Root F1 0.8

외부 PG 원인과 실제 증거 ID는 맞았다. 그러나 두 원인 중 하나를 누락했고 proof 규칙도 통과하지 못해 strict correct = false였다.

7. 모델의 실제 최종 답

실제 출력에서 핵심 필드만 발췌

긴 문장은 읽을 수 있는 길이로 줄였고, 내부 target UUID는 바로 아래에 실제 값과 서비스 이름을 함께 표시했다.

{
  "status": "provisional",
  "causes": [{
    "target": "2e6120e3-37fa-4c44-a224-6ab13afdd9ee",
    "target_name": "food-delivery-payment",
    "confidence": 0.6,
    "claim": "PG /pay 호출에서 429 RATE_LIMITED가 발생했고 payment 계열 장애로 전파됨",
    "proof_type": "unknown",
    "support_refs": ["ev010", "ev011", "ev221", "ev212", "ev210", "ev220"],
    "proof_valid": false
  }],
  "external_causes": [{
    "id": "external:pg",
    "kind": "external_dependency",
    "boundary_target": "2e6120e3-37fa-4c44-a224-6ab13afdd9ee",
    "evidence_refs": ["ev010", "ev011", "ev221", "ev212", "ev210", "ev220"]
  }]
}

맞게 조사한 내용

  • 외부 PG의 429 RATE_LIMITED를 찾음
  • 외부 호출 429와 인바운드 429의 연결을 설명
  • 실제로 조회한 증거 ID를 답에 포함
  • 완전 증명으로 과신하지 않고 provisional로 제출

틀리거나 빠진 내용

  • 독립된 inventory EXCLUSIVE lock 원인을 누락
  • commerce 오류 일부를 PG 장애 영향으로 잘못 연결
  • 결정적 증명 유형을 제시하지 못함
  • 두 원인이 서로 독립적이라는 반증을 완성하지 못함

8. 왜 부분 점수만 받았나

항목결과왜 이렇게 판정됐나
Root F10.8외부 PG root는 찾았지만 독립된 inventory lock root를 놓쳤다.
Reward0.572부분적으로 맞은 root, 유효 evidence refs, provisional status가 반영됐다.
Proof rate0결정적 proof type을 충족하지 못했다.
Evidence completefalse정답 root 전체를 설명하는 지지·반증 증거가 완성되지 않았다.
Strict correctfalse두 root 전체, 인과 분리, proof 계약을 모두 만족해야 통과한다.
최종 해석: 이 실행은 완전한 정답이 아니다. 학습 전 모델과 달리 실제 외부 원인 하나와 증거를 찾았기 때문에 부분 점수를 받았다. 그러나 두 번째 원인을 누락했고 증명도 완료하지 못해 strict correct는 실패했다. 현재 강화학습이 개선해야 할 항목은 “모든 독립 원인 찾기”, “원인별 증거 분리”, “결정적 증명 완료”다.
