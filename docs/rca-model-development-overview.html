Evidence-grounded agentic RCA

정답을 찍는 모델이 아니라,
증명하며 조사하는 모델

장애 징후를 보고 곧바로 원인을 말하는 분류기가 아니다. 실제 운영자처럼 도구를 선택하고, 관측을 시간축으로 연결하고, 경쟁 가설을 반박한 뒤, 인용 가능한 증거가 갖춰졌을 때만 원인을 확정하는 Student RCA 에이전트다.

핵심 하네스 계약 완료 SFT 완료 개선 RL 진행 중 공정 평가 진행 중 봉인 평가 대기
원본은 전부 보존한 번에 보여주는 양만 제한. 조회되지 않은 증거를 영구 삭제하지 않는다.
생각은 자유롭게가설 공간은 열어 두되, 실행 action·target·metric은 현실 계약을 통과한다.
결론은 증거로 제한원인·메커니즘·지지 증거·반증 증거가 연결돼야 confirmed가 가능하다.
01 · 문제 정의

그럴듯한 설명과 RCA는 다르다

RCA에서는 첫 이상 징후가 원인이라는 보장이 없다. 상관관계를 인과로 과장하지 않고, 필요한 관측을 스스로 찾아가야 한다.

일반 모델의 실패 패턴

  • 첫 로그나 metric spike를 근본원인으로 확정
  • 없는 metric·target·action 생성
  • 최근 관측만 남기고 초반 증거 유실
  • 도구를 호출했다는 사실만으로 confirmed
  • 최종 답에 증거 출처와 반증 과정 없음

우리가 학습시키는 패턴

  • 증상과 원인을 분리
  • 실제 가능한 도구와 metric 중 선택
  • 모든 성공·실패 관측을 ledger에 영속화
  • 원인 유형별 결정적 증명 규칙 적용
  • 근거 부족 시 provisional/insufficient 선택

예: HTTP 409는 “품절 응답”이라는 관측이다. 정상 품절인지, 재입고 배치 중단인지, 외부 RESTOCK 연동 실패인지 구분하려면 재고 전체 시계열과 유입 이벤트를 추가 조회해야 한다.

02 · Student 하네스

자유로운 에이전트에 현실 경계만 둔다

하네스는 답을 대신 찾는 규칙 엔진이 아니다. 모델이 안전하고 재현 가능하게 조사하도록 만드는 실험 환경, 도구함, 증거 기록부, 채점기다.

자유 영역 · Reasoning

원인 후보 생성, 다음 조사 계획, 경쟁 가설, 관측 해석은 자유롭게 수행한다.

“내부 CPU보다 외부 PG 경계 실패 가능성이 높다. trace로 실패 시작점을 먼저 비교하자.”
→

엄격 영역 · Execution boundary

action, target, metric, 시간 범위, 관측, 증거 참조, final answer는 구조 검증을 통과해야 한다.

target=payment-service
metric=실제 registry 등록값
support_refs=[obs-003]

Capability registry

이번 사건에서 실제 가능한 도구, 대상, metric, source, evidence kind의 동적 목록. 결제 서비스에 DB replica lag를 잘못 요청하거나, 없는 metric을 만들어 내는 행동을 실행 전에 차단한다.

증거 지도 + typed ledger

요약문 하나가 아니다. 원본 증거와 새 관측에 ev..., obs-... ID를 붙여 연결한 인덱스와 영속 기록부다. 초반 증거와 실패 호출도 사라지지 않는다.

03 · Student Tool Catalog

Student에게 준 도구 전체

모두 조사용 읽기 도구다. 운영 시스템을 변경하거나 복구 명령을 실행하지 않는다. note와 answer는 조사 상태를 기록·종료하는 제어 action이다.

증거 탐색Metric전문 Probe제어

env_top

첫 탐색

이상 점수가 높은 원본 증거를 우선순위대로 본다. 사건 전체를 빠르게 조망하는 출발점.

입력
보고 싶은 개수
출력
상위 evidence ID·대상·종류·요약
예: 상위 15건 → 오류율 spike, timeout trace, 변경 이벤트 후보

env_entity

대상 중심

특정 target에 연결된 증거를 모아 본다. 후보 서비스나 DB를 깊게 조사할 때 사용.

입력
target ID
출력
그 대상의 metric·log·trace·event 증거
예: payment-service에 연결된 모든 종류의 관측 후보 조회

env_query

구조 조회

문자열 grep 대신 target, source, kind, 시간 범위를 조합해 원본 증거를 정확히 찾는다.

입력
target/source/kind/from/to/limit
출력
조건에 맞는 evidence 목록
예: inventory-service + event + 09:55~10:05 + limit 12

env_aggregate

분포 확인

증거를 target·source·kind·metric별로 묶어 개수와 최대 이상도를 본다. 어디부터 파고들지 결정한다.

입력
구조 조건 + group 기준
출력
그룹별 count/max anomaly
예: target별 trace_error 수 → 결제 경계에 실패 집중

env_grep

보조 검색

원문에서 키워드를 찾는다. 구조 조회로 표현하기 어려운 용어를 찾는 보조 수단이며 주 탐색기는 아니다.

입력
검색 문자열
출력
일치 evidence
예: “RESTOCK”, “blocking”, “timeout”, “429”

env_slice

정확한 재열람

이미 찾은 evidence ID의 원문을 다시 꺼낸다. 최종 답 전 증거 인용을 확인할 때 유용하다.

입력
evidence ID 목록
출력
해당 원본 증거
예: ev039, ev045, ev052의 실제 내용 재확인

probe_metric

빠른 Metric

등록된 target·metric의 이상 여부를 빠르게 조사하는 호환 action. 결과는 ledger 관측으로 남는다.

입력
target ID + registry metric
출력
요약·이상 사실·시계열 접근 정보
예: order-service 오류율이 최초 장애 전부터 상승했는가

metric_overview

요약 보기

전체 point를 버리지 않으면서 min/max/변화와 같은 빠른 개요를 본다. 인과 확정용 원본 조회 전 탐색 단계.

입력
target ID + metric
출력
overview + total/returned/truncated 상태
예: 1,440 points 중 개요만 반환, 원본은 계속 보존

metric_describe

Metric 이해

metric의 단위, 수집 범위, point 수 등 해석에 필요한 메타데이터를 확인한다.

입력
target ID + metric
출력
설명·기간·point metadata
예: 비율인지 누적 counter인지 확인한 뒤 비교 방식 결정

metric_fetch_raw

전체 시계열

metric의 원본 전체 시계열을 가져오고 재인용 가능한 raw reference를 만든다. metric 인과·포화 확정의 핵심.

입력
target ID + metric
출력
전체 points + raw_ref + full-series 표시
예: CPU 한 점이 아니라 장애 전후 전체 곡선을 증거로 보존

metric_fetch_window

시간 확대

지정 시간창의 원본 시계열을 자세히 본다. 최초 장애 전후의 순서를 확인할 때 사용.

입력
target ID + metric + from/to
출력
해당 window points + raw_ref
예: 09:55~10:10 재고 수량과 10:02 오류 시작 비교

metric_compare

대상 비교

같은 metric을 두 target에서 비교해 공통 원인, 전파 방향, 특정 대상 문제를 구분한다.

입력
target A + target B + 공통 metric
출력
정렬된 두 시계열 비교
예: 정상 replica와 장애 replica의 latency 비교

discover_metrics

선택적 활성화

target에서 실제 조회 가능한 metric inventory를 발견해 registry를 확장한다. 자유 문자열 추측을 대신한다.

입력
target ID
출력
검증된 metric 이름 목록
예: 신규 서비스의 실제 metric을 찾은 뒤 다음 턴에 조회

probe_events

이벤트

대상의 경보·상태 변화·직접 이벤트를 조회한다. 원인을 직접 나타내는 사건이 있는지 확인한다.

입력
target ID
출력
시간순 event + 구조화 facts
예: batch failed, OOMKilled, pod restart 이벤트

probe_cohort

동료군 비교

같은 역할의 instance·replica·host 집단을 비교한다. 한 대상만 이상한지 전체가 이상한지 구분한다.

입력
target ID
출력
peer/cohort 이상 비교
예: replica 5개 중 1개에서만 오류율 급증

probe_db_blocking

DB Lock

대기 세션과 blocker 관계를 조사해 실제 blocking chain을 찾는다. DB blocking 확정의 결정적 도구.

입력
DB target ID
출력
blocker·waiter·세션·시간 facts
예: 장기 transaction → 주문 UPDATE 37개 대기

probe_topsql

SQL 부하

장애 구간의 비용·지연·호출이 큰 SQL을 찾는다. 느린 DB의 구체적 실행 경로를 좁힌다.

입력
DB target ID
출력
상위 SQL key·text·부하
예: inventory UPDATE가 총 DB 시간의 대부분 차지

probe_logs

로그

대상 로그를 시간창과 함께 읽는다. 증상·에러 문구를 찾되 로그 한 줄만으로 인과를 확정하지 않는다.

입력
target ID
출력
관련 log evidence + facts
예: connection pool exhausted 직후 HTTP 500 반복

probe_traces

호출 경계

분산 trace를 통해 실패가 시작되는 서비스·DB·외부 호출 경계를 찾고 전파 방향을 확인한다.

입력
target ID
출력
span error·latency·upstream/downstream facts
예: 내부 처리 정상, 외부 PG span부터 timeout

probe_changes

변경 이력

배포·설정·버전 변경이 최초 장애보다 앞섰는지 확인한다. 시간 선행은 필요조건이지 단독 증명은 아니다.

입력
target ID
출력
change event + version + timestamp
예: 09:58 배포, 10:02 장애 — 추가 영향 증거 필요

probe_db_query_events

DB 실행 사건

DB query 실행과 오류 이벤트를 시간순으로 조사한다. SQL key와 장애 시점을 연결한다.

입력
DB target ID
출력
query event·오류·세션 facts
예: lock timeout이 발생한 SQL과 호출 프로그램 식별

probe_replica_lag

복제 지연

DB replica의 lag와 상태를 조사한다. stale read나 read replica 지연 가설을 확인한다.

입력
DB target ID
출력
replica lag·상태·시간 facts
예: 주문 조회 실패 직전 replica lag가 수초로 급증

probe_host_peers

Host 연관

같은 host·인접 host의 peer 상태를 비교한다. 서비스 장애가 host 자원 문제에서 비롯됐는지 본다.

입력
target ID
출력
host kin/peer 이상 증거
예: 같은 node의 여러 pod에서 동시에 I/O 지연

probe_snmp_traps

장비 이벤트

네트워크·장비의 SNMP trap을 조회한다. 서비스 바깥 인프라 경계 문제를 조사한다.

입력
target ID
출력
trap type·장비·시간 facts
예: 장애 직전 switch interface down trap

sub_summarize

기본 비활성

선택한 evidence ID 묶음을 보조 LLM이 요약한다. 원본을 대체하지 않으며, 현재 정책에서 필요할 때만 활성화한다.

입력
evidence ID 목록 + 질문
출력
참조가 유지된 보조 요약
예: 12개 trace의 공통 실패 경계만 정리

note

조사 메모

현재 가설, 반박된 후보, 다음 조사 계획을 episode에 남긴다. 운영 환경은 변경하지 않는다.

입력
구조화할 조사 메모
출력
ledger에 남는 note
예: “배포 가설 약화. 외부 PG trace를 다음에 확인.”

answer

종료 action

조사를 끝내고 원인·메커니즘·증거·확신 상태를 제출한다. proof 계약이 부족하면 confirmed가 거절된다.

입력
status, causes, external_causes, refs, ready
출력
검증된 RCA 결과 또는 계약 오류
예: confirmed + DB blocking + support_refs=[obs-007]

검색 조건에 맞는 도구가 없다.

04 · End-to-end Example

HTTP 409에서 재입고 중단까지

같은 증상이라도 원인은 여러 개다. 아래는 Student가 도구와 ledger를 사용해 경쟁 가설을 분리하는 예시다.

성급한 결론

관측: HTTP 409 급증

결론: 정상 품절

문제: 재입고 중단과 구분할 증거 없음

VS

목표 조사

가설: 정상 품절 / 배치 중단 / 외부 RESTOCK 실패

방법: 시계열·이벤트·변경·외부 경계를 시간축으로 연결

1
env_aggregate

관측
409와 inventory 관련 증거가 한 시간창에 집중.

해석
재고 계층을 우선 조사하되 아직 원인은 미정.

2
metric_fetch_window

관측
09:55부터 재고 감소, 10:02 이후 0 유지.

해석
409는 재고 고갈의 결과. 회복 이벤트 확인 필요.

3
env_query

관측
평소 10:00 RESTOCK 유입이 장애일에는 없음.

해석
정상 품절보다 공급 경로 중단 가설 강화.

4
probe_events

관측
09:59 재입고 batch failed 이벤트.

해석
시간 선행 확인. 배치 실패 메커니즘 조사.

5
probe_logs

관측
외부 warehouse 인증 실패로 RESTOCK fetch 중단.

해석
배치 실패 → 유입 부재 → 재고 고갈 → 409 사슬 성립.

6
answer

지지
obs-002 재고 시계열, obs-004 batch failure, obs-005 인증 실패.

결론
외부 경계까지 직접 확정 가능한지에 따라 confirmed 또는 provisional.

05 · Teacher Data

한 번의 정답이 아닌 재귀적 조사

교사는 답 문장 하나를 만드는 게 아니라 조사하고, 비평받고, 정답을 노출하지 않는 교정을 받아 다시 조사한다.

1독립 조사

정답을 보지 않고 하네스 실행

2Critic/Scorer

증거·형식·확신 검증

06 · Training

SFT로 습관을 만들고, RL로 선택을 다듬는다

각 턴을 독립 샘플로 쪼개지 않는다. 앞 관측이 다음 도구 선택의 이유이므로 한 사건의 전체 multi-turn episode를 학습 단위로 사용한다.

SFT · 전체 episode 모방

오류율 확인변경 확인trace 경계 확인DB blocking 확인경쟁 가설 반박증거 포함 답변

assistant 응답에만 loss를 적용하지만, 사용자 입력·action·tool observation은 문맥으로 통째로 유지한다. base 전체가 아니라 LoRA adapter를 학습한다.

Chosen trajectory

구조 조회 → 전체 시계열 → trace → blocking chain → 메커니즘과 evidence refs → 올바른 confirmed

>

Rejected trajectory

grep 반복 → 성급한 추측 → proof 없음 → 증거 ID 없이 confirmed

RL v6 · Whole-trajectory RPO

SFT 모델 위에서 전체 조사 궤적의 상대 선호를 학습한다. 좋은 궤적을 나쁜 궤적보다 높이는 preference loss에 작은 imitation/NLL anchor를 함께 둬, 이미 잘하던 SFT 정책이 무너지는 것을 억제한다. 모델은 adapter 형태로 유지한다.

07 · Evaluation Contract

정답뿐 아니라 증명 품질을 채점한다

평가와 RL 학습용 성공·실패 판정은 같은 typed scorer 계약을 기준으로 한다. 근거 없는 confirmed는 큰 penalty를 받는다.

외부 의존성내부 정상 구간과 외부 경계 실패를 연결하는 관측

학습셋 모니터

대표 train 6 case × 3회. 기본 조사 능력과 퇴행을 빠르게 확인한다.

봉인 평가

완전히 격리한 12 case × 3회. 최종 성능 순위는 이 결과로만 주장한다.

08 · Current State
