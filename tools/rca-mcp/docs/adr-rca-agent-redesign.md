# RCA agent 재설계 — 합의된 결정

## 목적과 규율

이 문서는 2026-07-22~23 재설계 논의에서 **하나씩 합의한 결정만** 기록한다.

배경: 앞선 작업에서 분석·설계·문서화가 한꺼번에 진행되며 합의하지 않은 내용까지
문서에 들어가고 방향이 지나치게 규칙 중심으로 흘렀다. 그 교정으로, 이번에는 구현·
문서화를 서두르지 않고 열린 쟁점을 하나씩 논의해 합의한 것만 여기 남긴다.

규율:

- 이 문서에는 **합의된 결정**만 넣는다. 아직 안 정한 것은 "열린 항목"에 명시한다.
- 구체 알고리즘·수치·인터페이스처럼 합의하지 않은 세부는 넣지 않는다("나중에"로 표시).
- 기존 정본 스펙(`spec-agent-*`)은 이 논의로 **아직 갱신하지 않았다**. 충돌하는 부분은
  이 문서가 방향을 대신하되, 스펙 반영은 별도 작업이다.
- `adr-rca-improvement-direction.md`와 `ref-lucida-next-rca-data-inventory.md`는 이 논의
  **이전에** 다른 작업에서 나온 초안으로, 이 문서가 승인하거나 대체하지 않는다.

## 관통 원칙

10개 결정을 관통하는 하나의 방향:

> **작은 모델(조사자)을 규칙으로 옭아매는 대신, 모델에게 보여주는 것을 코드가 잘 깔아준다.**
> 규칙 중심의 판정 철학은 덜어내되, 무엇을 근거로 무엇을 이었는지에 대한 **감사 가능성은
> 유지**한다. 확정 문턱·예산 같은 수치는 실제 주행으로 보정한다(재보고 정하기).

## 합의된 결정 (10건)

### D1. 분석 방식 = 증상 따라 파고들기

원인 후보를 미리 N개 세우고 하나씩 배제하는 방식이 아니라, 증상에서 시작해
따라 내려가며 조사한다.

### D2. 조사 상태는 코드가 소유하는 "보드"에 담는다

보드에 담을 것: ① 지금까지 밝혀진 인과 이야기 ② 안 가본 갈림길 ③ 확인해서 배제한 것
④ 다음에 뭘 할지·언제 멈출지 판단할 재료.

보드의 소유권은 **코드**에 있다(모델은 정돈된 보드를 보고 판단만 한다). LangGraph의
*state*처럼 코드가 상태를 들고 다니되, 노드·엣지를 미리 그려 고정하는 그래프는 쓰지
않는다(다음 행동은 그때그때 모델이 정한다). 모델은 보드 전체를 다시 쓰지 않고 **작은
변경분만 제안**하고, 코드가 append 한다.

### D3. 보드의 주인공 = 자라는 인과 이야기 + 갈림길

가설(원인 후보)은 처음부터 목록으로 세우지 않고, **길이 갈릴 때만 등장하는 조연**이다.
이로써 "초기 후보 밖의 새 원인을 어떻게 발견하나"는 고정 후보 우주 문제에서 탐색
frontier 문제로 옮겨간다(→ D5).

### D4. 보드 내부 정본 = 사실 카드 + 딱지 붙은 인과 화살표 + 갈림길

내부 기록은 자유 서사가 아니라 구조를 갖는다.

- **관측 사실 카드**: 도구가 실제로 반환한 사실(window/scope/원본 ref 포함).
- **인과 화살표(A→B)**: 각 화살표에 상태 딱지 — `추측 / 뒷받침됨 / 검증됨 / 반박됨`.
- **갈림길**: 아직 가르지 않은 대안.

"이야기"는 사람에게 보여줄 때 이 위에서 뽑아내는 겉표현이다. 사실과 추론을 섞지 않고
화살표마다 상태를 명시함으로써, 근거는 붙었지만 실제로는 틀린 이야기가 통과하는 것을
막는다. 딱딱한 관문(규칙)은 붙이지 않되, append-only 기록의 감사 가능성은 유지한다.

### D5. 새 원인 발견의 레버 = discovery frontier (코드가 후보 관점을 legible하게 깔아줌)

"코드가 넓히기 타이밍을 강제"하는 방식은 **기각**한다. 대신 코드/도구가 "아직 안 가본
중요한 구역"을 눈에 보이게 깔아주고, 모델이 스스로 그리로 넓히게 한다.

근거: 가짜 세계 spike 3종(쉬움 / 미끼+잡음 / 대규모 이웃)에서 실제 소형 모델
(gemma4-26b)이 자율(A) · 코드강제(B) 모두 3/3으로, 스스로 관점을 바꿔 토폴로지 밖
원인에 도달했다. 세계가 legible하면 소형 모델도 스스로 넓힌다. 실패의 병목은 "넓힐지
결정"이 아니라 "**무엇으로 넓힐지가 안 보임**"이다.

**정련 (2026-07-23 실 주행 검증 — 아래 "검증 기록" 참조):** blind 프론티어
주행에서 가장 값진 넓히기 두 건은 legible한 *후보 관점 목록*이 아니라, 코드가
내준 **비교 가능한 수치에 대한 추론**에서 나왔다 — "이 생산율로는 이만큼 밀릴 수
없다"(양적 모순), "또래 서비스는 정상인데 이것만 이상"(비대칭). 따라서 D5의
legibility 레버의 핵심은 후보를 나열해 보여주는 것보다 **코드가 rate·capacity·lag·
또래를 나란히 계산해 하나의 사실로 내주는 것**이다(→ D10과 묶인다). 소형 모델은
날숫자를 눈대중해 이런 모순·비대칭을 스스로 잡기 어려우므로, 이 비교는 코드 몫이다.

### D6. 한 걸음 = 한 진단 질문 (기본 하나씩)

한 걸음은 "정돈된 보드를 본다 → 다음 질문 하나를 정한다 → 코드가 조회를 실행해 보드에
기록한다 → 모델이 판단한다(이야기 연장 / 갈림길 열기 / 배제 / 종료)"이다. 기본은
하나씩이며, 넓게 보는 것은 D5의 frontier가 담당한다.

### D7. 멈춤 ≠ 확정

- **멈춤(종료)**: 조사를 그만두는 것. 이유를 유형으로 기록한다 —
  `원인 충분 / 수단 소진 / 새 정보 없음 / 예산 / 못 하는 도메인`.
- **확정**: 결론에 원인 딱지를 박는 것. 별도 문턱을 통과해야 한다 — 원인 대상과
  메커니즘이 있고, 증상까지 화살표가 `검증됨` 딱지로 이어지고, 결론을 뒤집을 만한 안
  가른 갈림길이 남지 않았을 것.

"더 팔 수단이 없어서 멈춤"은 확정이 아니라 대개 미확정(provisional)이다. 과거의
"경쟁 가설 전원 배제" 같은 과한 요구는 두지 않는다. 확정 문턱의 정확한 빡셈 정도는
실제 주행으로 보정한다(지금 수치로 못박지 않음).

### D8. 검증 = 코드 기계 대조 + 승격 시 좁은 확인 + 확정 직전 통짜 도전

"매 걸음 blind 검증자"는 두지 않는다(같은 소형 모델을 매번 다시 부르는 것은 독립
검증이 아니고, 원본 없이 요약문만 보는 검증은 문장 정합 검사에 가깝다). 대신:

1. **코드 기계 대조**를 먼저 — 증거 ref가 실재하는가, 관측값이 화살표 주장과 맞는가.
2. 화살표를 `검증됨`으로 **승격하는 순간에만** 좁은 LLM 확인 — 그 화살표에 걸린 원본
   증거를 실제로 펼쳐 뒷받침 여부만 판정.
3. **확정 직전 한 번** 통짜 도전자 — 안 가른 갈림길·반대 증거가 없는지 전체를 흔든다.

### D9. 조사자 하나 + 상황별 도구 메뉴

역할을 여러 agent로 쪼개지 않고, 조사자 하나를 두되 도구 메뉴를 상황에 맞게 좁힌다.

- **일상 공구(약 7개)** 는 늘 보인다: 둘러보기(신호 발굴) · 지표 · 트레이스 분해 ·
  런타임 의존성 · 로그 · 이벤트 · 차원 쪼개기.
- **도메인 공구**(DB 세션·슬로우쿼리·SNMP trap·K8s 상태 등)는 **그 도메인이 이야기에
  들어올 때만** 메뉴에 등장한다.

어느 순간에도 메뉴는 8~10개 수준이며, 18개를 동시에 노출하지 않는다. 도메인 전문가로
agent를 분리하는 방식은, 한 조사자가 특정 도메인을 너무 얕게 판다고 판단될 때 나중에
검토한다.

### D10. 코드/LLM 경계 — 데이터 "읽기"는 코드가 계산해 사실로 준다

- **코드 = 눈**: 원천 조회, 식별자 정규화, 단위·타입 맞춘 계산, 진단 primitive
  (선행/후행 lead-lag, 범위 겹침, 같이 움직임, onset/recovery), coverage, 원본 ref.
- **LLM = 머리**: 그 사실들로 가설·화살표·다음 수·종합 판단. **raw 시계열을 눈대중
  하지 않는다.**

primitive의 구체 알고리즘(임계값, change point, seasonality 처리)은 까다로우므로 지금은
원칙만 고정하고 알고리즘은 나중에 정한다.

## 검증 기록 — 첫 실 주행 (2026-07-23)

열린 항목 첫 줄("프론티어 모델의 조사 궤적을 설계 참고로 쓸지")을 **채택하고 처음
돌렸다.** 큰 모델(Opus)을 **정답을 모르는 blind 상태**로 실 케이스(F04-R — shipping의
Kafka consumer 중단으로 배송 생성 지연)에 풀고, 도구 18종을 하나씩 부르는 진입점
`cmd/tool`로 자유 조사시킨 뒤 궤적을 관찰했다. (직접 SQL·케이스 문서 접근은 막아,
소형 모델과 **같은 도구 표면**만 쓰게 했다 — 관찰한 궤적이 하네스로 전이되도록.)

결과: 16걸음에 원인에 정확히 도달했고(listener ~7분 정지 → 백로그 → 배송 지연),
동시에 겹친 트래픽 급증(distractor)을 "또래 consumer는 밀리지 않았고 이것만 멈췄다"는
비대칭 논거로 **악화 요인으로 강등**했으며, 일곱 개 갈림길을 각각 특정 증거로 배제했다.

**검증된 것:**

- **D1·D3** — 후보를 미리 세우지 않고 증상에서 파고들었다. 가설(rebalance·broker
  장애·DB 락·GC·급증)은 전부 **갈림길에서만** 등장했다.
- **D7** — 원인에 도달했으되 "정확한 트리거"는 확신 낮음으로 못박고 무엇이 빠졌는지
  명시했다(과확신 억제가 실제로 작동).
- **D5** — 정련됨(위 D5 참조): 넓히기 레버의 핵심은 후보 목록이 아니라 코드가 내준
  비교 수치라는 것이 드러났다.

**드러난 도구 사각지대** (소형 모델 하네스로 넘기기 전에 고칠 것 — 이 케이스의 마지막
한 조각을 강모델조차 확정 못 하게 만든 원인):

1. 평범한(INFO) 로그 본문이 안 보인다(`get_logs`가 WARN+ 템플릿만) — 무엇이 listener를
   멈췄는지가 INFO 줄에 있는데 못 읽어, 이 케이스가 완전 확정에 못 이른 **유일한** 이유.
2. consumer/listener 처리 구간이 트레이스 도구에 안 보인다(SERVER span만) — Kafka
   구동 서비스는 불투명.
3. episodic gauge(rebalance)가 `discover_signals`에서 "신규 등장"으로 떠 **첫 가설을
   오도**했다.
4. topology의 DB 이웃이 UUID 없는 문자열(`db:postgresql`)이라 DB 세션·락 도구를 못 건다.
5. baseline "무관측"이 measured-zero와 no-sample을 구분하지 않는다.
6. Kafka topic/consumer-group 계보가 없어 넓히기가 결정론이 아니라 추론에 의존했다.

**거리 주의:** 프론티어는 강모델(Opus), 프로덕션은 소형(gemma4-26b)이다. 관찰된
자기교정·교차메트릭 산술을 소형 모델이 재현한다는 보장은 없다. 증류 방향은 **"강모델을
성공시킨 것을 코드가 대신 공급"**(비교 수치 primitive, 기계 대조)이다.

이 검증은 결정을 바꾸지 않고 뒷받침한다. 위 사각지대와 D5 정련은 `spec-agent-tools`·
소형 모델 하네스 작업의 입력이다(별도 작업). 근거: `cmd/tool`(신규 진입점), 궤적 원본은
세션 스크래치패드 `frontier-trajectory-f04r.md`.

- 정본 스펙 `spec-agent-design.md` · `spec-agent-tools.md` · `spec-agent-ledger.md` ·

  반영은 아직 하지 않았다(별도 작업).
- `adr-rca-improvement-direction.md` · `ref-lucida-next-rca-data-inventory.md`는 이 논의
  이전의 초안으로, 이 문서가 승인·대체하지 않는다. 유용한 관찰(예: 관계 분석의 필요,
