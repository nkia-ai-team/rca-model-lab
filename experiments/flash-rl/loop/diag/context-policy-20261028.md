# 컨텍스트 정책 변경 (rolling8 → budget) 과 기준선 재측정 계획 — 2026-10-28

## 원인
- 학습 처리량은 일정하다 (~520 computed tok/s). 에피소드 시간 = computed 토큰 수.
- `rolling_view`(rollout·SFT·학습 공용) 가 최근 도구 결과 8개만 원문으로 남기고 더 오래된 결과를 1200자로 줄인다. 새 결과가 하나 들어올 때마다 9번째 결과가 줄어들어, 매 턴 히스토리 중간이 바뀐다 → prefix 트리 공유가 끊기고 꼬리 1~1.5만 토큰을 재계산.
- 학습 그룹 4개: computed 5.64M vs append-only 1.72M (3.3x).
- 하이브리드 구조 (36 GDN + 12 full attn, KV 2헤드): 위치당 비용은 MoE FFN 이 대부분이라 긴 컨텍스트 자체는 싸다. 반면 중간을 고치면 그 뒤의 recurrent state·KV 를 모두 다시 계산해야 한다 → "가끔 크게, 나머지는 덧붙이기만" 이 구조상 맞는 방향.

budget: 프롬프트 경계에서 뷰가 140k자를 넘으면 마지막 8개를 뺀 나머지를 한 번에 줄이고, 줄인 건 계속 줄인 채로 둔다. 판단은 메시지만으로 결정되는 순수 함수라서 (경계마다 재생) rollout 과 학습의 뷰가 같다.

알려진 퇴화: 최근 8개 원문만으로 예산에 가까워지면 매 턴 압축이 일어난다. 실데이터 규모(8개 ≤ ~48k자)에서는 일어나지 않는다.

## 기준선 재측정 계획 (Codex 토픽 4, 2라운드 합의)
0. 시작: 스윕 + held-out 채점 종료 후 (~15:15 KST). 스윕은 건드리지 않는다.
1. **동시 paired 대조**: u062 × {rolling8, budget}
   - 두 서버에서 교차 실행하고, 서버 배정은 정책별로 균형을 맞춘다.
   - 케이스·시드·디코딩·도구 바이너리·한도는 동일하게 둔다.
   - 트랙: validation10 ×2, new13 ×2, public12 ×1 (팔당 58, 총 116 에피소드, ~3h).
   - 에러·타임아웃은 실패로 센다 (따로 보고).
2. **사전 선언한 판정** (joint, budget − rolling8)
   - 케이스 35개로 paired 비교한다.
   - 트랙별로 케이스를 통째로 재표집하는 bootstrap 90% 구간을 쓴다.
   - 판정:
     - 잠정 채택: 합계 ≥ −2, 어느 트랙도 −3 이상 나빠지지 않음, 구간 하한 > −6
     - 보류: 합계 ≤ −5, 또는 어느 트랙이 −4 이상 나빠짐
     - 그 외(불확정): rolling8 유지, budget 은 측정용 ablation 으로만 사용. 일부 케이스만 골라 재실행해 판정에 합치지 않는다 (진단용으로만).
   - "잠정" 이다: 비열등성을 증명한 것은 아니다 (구간 하한 −6 = 10.3%p 손실까지 허용).
3. **속도 실측**
   - rollout: 턴, 생성 토큰, 프롬프트 p50/p95/max, 압축 이벤트, vLLM prefix cache hit (창 단위 metrics 차분), prefill 지연.
   - 첫 학습 업데이트: computed 토큰, s/episode.
   - 압축 경계와 긴 프롬프트에서 기록된 prompt token ID 와 렌더 결과를 표본 대조한다.
4. **확인 시험** (스윕 finalist 2 + u062, dev 6케이스 ×4)
   - budget 으로만 돌린다. 목적은 배포 선택이다 (optimizer 귀속은 안 함).
   - 1이 불확정·보류면 rolling8 로 돌린다.
5. **milestone 기준선** (public 113, sealed 12×2, original12 ×2) u062: 판정 후 채택된 정책으로 측정하고, 보고 전용으로만 쓴다.
6. 루프 재개: `context_policy` 확정, 새 epoch 기준선만 사용.

보류: 토큰 기준 예산, 삽입 시점 압축, reasoning 유지는 별도 실험으로 미룬다.
